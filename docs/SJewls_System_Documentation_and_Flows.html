🌱 Beginner Introduction & Core Concepts

Understanding the modern web application stack and .NET Clean Architecture principles through concrete examples in SJewls.

Frontend vs. Backend

Frontend: Code that runs on the user's device (browser or phone). In SJewls, this is admin/src/app (Next.js) and the React Native mobile client.

Backend: The secure C# server (SJewls.Api) that validates rules, manages transactions, queries PostgreSQL, and hashes secrets.

User Interface vs. C# Interface

User Interface (UI): The visual screen with buttons, inputs, and tables (e.g. admin/src/app/jewellery-plans/page.tsx).

C# Interface: A code contract in C# (e.g. ICustomerAuthService) declaring available methods without code. A service class then implements it.

DTO & Dependency Injection

DTO (Data Transfer Object): A plain C# class carrying data over HTTP (e.g. CheckContactRequest).

Dependency Injection (DI): .NET automatically injects service classes into endpoints at runtime rather than creating them with new.

EF Core, DbContext & Migrations

EF Core: Object-Relational Mapper that turns C# objects into SQL.

DbContext (SJewlsDbContext): The active database session.

Migrations: C# scripts updating PostgreSQL tables automatically.

Summary of Workflows B through J
Workflow B: Staff Auth

Staff login via username/email & password. Verifies password hash. Returns JWT with claims (ManagePlans, ManagePayments, ViewEnrolments) and assigned branch IDs.

Workflow C: Customer Management

Admin in-store registration validates unique NIC and mobile. Closing an account marks Status = Closed while keeping historical investment ledgers intact for legal compliance.

Workflow D: Plan Administration

Admin defines target grams, offered duration options, and premium %. Modifying a plan never alters active enrolments; target grams & premium % are snapshotted permanently at enrolment.

Workflow E: Mobile Enrolment

Customer joins plan from mobile. Repeat check guards against duplicate joins. Enrolment is created in Active status immediately with 0 initial deposit.

Workflow F: Admin Plan Assignment

Staff selects customer and plan in-store. Target grams is read-only from the plan definition. Plan appears immediately in customer's mobile "My Investments".

Workflow G & H: Payment Finalization

In-store cash/card payment creates immutable JewelleryContribution, increments sequential payment number, updates gold balance, and triggers completion notification when target is met.

🔍 Findings, Verification & Limitations

Categorized audit findings distinguishing verified code features from deferred roadmap items.

✅ Confirmed from Code
  • Atomic Ledger: Payment recording runs inside an atomic EF Core transaction, ensuring enrolment balances and contributions remain 100% consistent.
  • Repeat Guard: Both Mobile and Admin enrolment reject duplicate active plans with HTTP 409 unless confirmed.
  • Separate Scalar Specs: Admin and Mobile APIs have isolated Swagger docs at /scalar/admin and /scalar/mobile.
⏸️ Inferred & Deferred
  • Online Payment Gateway: Mobile checkout initiation returns HTTP 501 NotImplemented (PaymentProviderNotConfigured). In-store staff payments are currently the primary rail.
  • Gold Markup Spread: Future rate adjustment percentage is deferred; the live rate is used directly.
  • Push Notifications: In-app notifications are active in PostgreSQL, but push tokens (FCM/APNs) are not yet dispatched.
🌐 Runtime Verification Needed
  • GoldAPI.io Quota: Ensure 15-minute in-memory caching duration is sufficient for production load.
  • Text.lk Telco Sender Mask: Verify that the sender mask SJewls is registered with Sri Lankan telcos.
  • Supabase Storage Policies: Ensure S3 bucket policies restrict public receipt downloads.
